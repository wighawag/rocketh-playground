# `$lib/playground`: compile, transpile and run, in four workers

The playground's core: what turns the project's files into a run of its deploy scripts. Plain `.ts`, no Svelte, no `$app/*`; each worker entry is a thin file over a module the node tests drive directly (`test/lib/playground/`).

| Thread | Entry | Logic | In | Out |
| --- | --- | --- | --- | --- |
| TypeScript worker (module) | `typescript/typescript.worker.ts` | `typescript/typescript-host.ts`, `typescript/transpile.ts`, `typescript/language-service.ts` | project files, artifact types | CommonJS per file, run-time imports, syntax diagnostics; the editor's diagnostics, completion and hover |
| compiler worker (CLASSIC) | `compiler/compiler.worker.ts` | `compiler/compiler-host.ts`, `compiler/solidity.ts` | the soljson URL, then project files | load progress, solc diagnostics, `generated/artifacts/*.js` and their `.d.ts` |
| EVM worker (module) | `evm/evm.worker.ts` | `evm/evm-host.ts` | node options, an IndexedDB name | webevm's node proxy; `serveOn(port)` |
| runner worker (module) | `runner/runner.worker.ts` | `runner/runner-host.ts`, `runner/run.ts` | a port the EVM worker serves; transpiled modules | log entries, deployment store changes, the outcome |

- **The editor is `editor/code-editor.ts`**, CodeMirror 6 on the page's thread (`components/playground/CodeEditor.svelte` mounts it): TypeScript syntax for `.ts`, `@replit/codemirror-lang-solidity` for `.sol`, records read-only. It is presentation only. Every edit goes to the session, which holds the text, so switching files keeps what was typed; the view is rebuilt when the file, the language service or the artifact types change (that loses the undo history at those moments).
- **The language service lives in the TypeScript worker**, beside the transpiler, through `@valtown/codemirror-ts` and `@typescript/vfs` (`typescript/language-service.ts`). The syntax-only editor is usable first; the session starts the language service once the rest has booted, and the editor attaches it when it is ready. It types the project with `hardhat-deploy init`'s compiler options plus the `webworker` lib (`typescript/project-options.ts`: `console` resolves, `document` does not, as in the runner). A type error never blocks Deploy: a run is transpiled, not type-checked.
- **Its declarations are a build asset**, not part of the worker: `scripts/declarations.mjs` records what TypeScript reads to type a file importing every package in `runner/bare-modules.ts` (and the type-only `rocketh/types`), lays it out npm-style (a second version of a package, such as viem's abitype, nested under its dependent), and `vite.playground.ts` writes it to `typescript/generated/declarations.json` (git-ignored), which the worker imports `?url` and fetches when the language service starts.
- **Artifact types before Deploy.** `compiler/solidity.ts` writes a `.d.ts` beside each generated `.js`, as hardhat-deploy's "javascript" generator does (`export declare const Artifact_<Name>: <the artifact as a literal type>;`); that is what types `artifacts.Counter` and makes a wrong constructor argument an error. The session compiles in the background as soon as the compiler is ready, and again after an edit to a `.sol` file (debounced), keeping the last types while a contract does not compile.
- **The page's side is `session.ts`**: a Svelte store holding the files, the transcript, the records and the chain's height, with `start`, `deploy`, `stop`, `reset`, `edit` and `select`. The workers are a parameter (`workers.ts` makes the browser's), and so are the IndexedDB databases, `chainDB`, `deploymentsDB` and `filesDB` (`web/src/lib/index.ts` names the browser's), so `test/lib/playground/session.test.ts` runs a whole session with each host on a MessageChannel (`language-service.test.ts` drives the language service alone); `e2e/tests/playground.e2e.ts` runs it in Chromium against the build.
- **The reader's files survive a reload.** With `filesDB`, `start()` first opens the project saved there (`project/saved-project.ts`): the files in `@rocketh/web`'s `createPersistentVFS` over `createIndexedDBPersistence`, and the selected file beside them (one object store, `project`, keys `files` and `selected`), or the starting project when the database is empty. Only then do the background compile and the language service start, so they see the restored files. Every `edit` and `select` is written back as it is made, and `dispose()` waits for the last write. A selected record that no longer exists falls back to the first deploy script; a database that cannot be opened leaves the session working from memory, with a warning in the transcript. `saved-project.ts` imports `@rocketh/web/dist/persistence.js` by path rather than the package's root, because the root also brings rocketh (and viem through it) into the page: the store adds about 4 KB raw, 1.5 KB gzip, to the first load (`docs/spikes/persist-project-files/measure-first-load.mjs` measures it).
- **Reset gives a first visit again**, saved copies included: the starting project's files, a fresh chain at block 0 and no records, so a reload after it opens the same. The header's Reset button asks for confirmation first (the UI kit's dialog) and is enabled only while the session is `ready`; `session.reset()` refuses otherwise, so no compile, run or write can land on the new chain. Stop restarts the runner and leaves the chain alone; Reset is the one action that touches the chain. In phase `resetting` it ends the runner and the EVM worker, then starts both again with `fresh`: the EVM host (`evm/evm-host.ts`) creates a node that ignores what `chainDB` holds and saves its genesis over it, and the runner host (`runner/runner-host.ts`) empties the deployment store and saves that before it reports `ready`. The files are restored over the saved ones (`SavedProject.reset`), the first deploy script is selected, the language service is given the starting files (the files the reader added are removed from it, `removeFiles`) and the background compile their artifact types; the diagnostics, the last run and the named accounts are cleared. The transcript is kept, with a line saying what Reset did, and the page closes a Contracts or Transactions view that was open (the Transactions list starts again from the new head, as it does whenever the head goes down).
- **Download saves the project as a hardhat-deploy project zip**, `rocketh-playground-project.zip`, one folder ready for `pnpm i && pnpm hardhat compile && pnpm hardhat deploy` (`project/export-project.ts`). It is every file of the template with the reader's files over them, less any starting file (`STARTING_PROJECT_PATHS`) the project does not hold: what the tab held is what installs, so a project opened from a bare `2.` link, which has no `contracts/Counter.sol` or `deploy/01_deploy_counter.ts`, does not get them back, and `pnpm hardhat deploy` does not deploy a `Counter` the tab never ran. In `package.json`, `workspace:*` becomes the published hardhat-deploy version (`TEMPLATE_SOURCE.version`), and every package the template shares with `web/package.json` gets the version pinned there, so what ran in the tab is what installs; a package `web/package.json` gives only a range (`@types/node`) keeps the template's, and no package is removed. Dependencies are declared by importing them: every package a project file imports (`import`, `export ... from`, `import()` or `require`, type-only imports included, read from the files' text by `importedPackages`) that the template's `package.json` does not list is added, at the version `web/package.json` pins, in the section where the template keeps `rocketh` (`devDependencies`), so a config spreading `@rocketh/router` or `@rocketh/diamond`, which the template does not depend on, installs them. Every package the runner resolves is pinned exactly there (`export-project.test.ts` checks it), so whatever ran in the tab is added; a package with no exact pin has no version the tab ran, and is not added. A project importing only the template's packages downloads exactly as before. The template's README is kept, opened by a section saying where the project comes from, naming the commands and stating MIT (the template's licence; only the playground's own code is AGPL-3.0). It never holds the deployment records (their chain only existed in the tab; any `deployments/` path is left out) nor a test key (the runner puts them into the config at run time, and no file holds them). The template's tests of Counter (`contracts/Counter.t.sol`, `test/Counter.ts`), which the reader never sees, are kept while `contracts/Counter.sol` is the template's and left out once the reader changed it: `hardhat build` also compiles Solidity tests, so a test calling a renamed function would stop `pnpm hardhat compile`. They are left out too when the project lacks either file of the Counter sample (`COUNTER_SAMPLE_PATHS` in `project/template.ts`), since `test/Counter.ts` expects a `Counter` deployment. The README's opening section says which template files were left out and why. A project holding every starting file, unchanged or with other edits, downloads byte for byte as it did before this rule. The header's button goes through `project/download.ts` (a store: building, or failed with the reason shown beside the button), offered once the files are open and not while Reset replaces them; it imports `export-project.ts` on the first press, so fflate is not in the first load (measured with `docs/spikes/persist-project-files/measure-first-load.mjs`: 885,754 B raw / 288,466 B gzip before, 887,387 / 289,137 after, the button and its store; the zip chunk, fflate with `export-project.ts`, is 13,182 B raw / 6,467 B gzip, loaded on the first press). `test/lib/playground/export-project.test.ts` unzips the export of the starting project, of an edited one and of a bare one.
- **The export installs and deploys**, checked by `pnpm test:export` (from the repository root; `web/vitest.export.config.ts`, `test/export/installs-and-deploys.export.ts`). It takes the zip `zipProject` builds, as Download does, for the starting project, for one whose `contracts/Counter.sol` was changed (a renamed function, a constructor argument, the deploy script passing it, so the Counter tests are left out), for a bare link's project (`bareProject()` with the bare vector's Greeter files over it: the Counter sample and its tests are left out, and `pnpm hardhat deploy` deploys `Greeter` and no `Counter`), and for one importing packages the template lacks, unzips each into a temporary folder and runs `pnpm i`, `pnpm hardhat compile` and `pnpm hardhat deploy` (hardhat's in-memory network) with whatever `pnpm` is on `PATH`; a step that fails fails the test, named with the end of its output, which a third case checks with a package pinned to a version that does not exist. Nothing is written to a shared location: the pnpm store (`pnpm_config_store_dir` and `npm_config_store_dir`, for pnpm 11 and 10) and every XDG folder (pnpm's metadata cache, hardhat's compiler cache and config) are inside the temporary folder, the variables pnpm and vitest add to a test run are not passed on, the test asserts that none of the files it wrote below its store or hardhat cache was also written below the real ones during the run, and it removes the folder. It needs the network and takes from seconds to minutes, so it is not part of `pnpm test` or `pnpm verify`; it is run by hand, and is what a rocketh release should pass before the playground follows it. Its offline parts (unzipping, the environment, a failing step named, the shared-folder check) are tested in `pnpm test`, `test/export/install-export.test.ts`.
- **Share puts the project in a link**, in the URL fragment, which the browser never sends to a server: `#project=1.<base64url>`, one key of the `key=value` pairs the page reads its fragment as (`web/src/lib/index.ts`, `hashParams`). The value is the files as JSON, deflated with fflate, in base64url without padding; `1.` names that encoding, so a later one can be told apart (`project/share-link.ts`, plain `.ts`, `test/lib/playground/share-link.test.ts`). A link carries at most 32 KB of fragment (`SHARE_FRAGMENT_LIMIT` in `project/link-fragment.ts`), measured as it is written, `project=` and the value: above that, Share says how big the link would be and offers Download instead. The header's Share button goes through `project/share.ts` (a store: the link, whether the clipboard took it, or too big), offered when Download is; it shows the link in a field as well as copying it, so a browser that refuses the clipboard still gives it. It imports `share-link.ts` on the first press, so fflate stays out of the first load (885,754 B raw / 288,466 B gzip before Download, 887,387 / 289,137 after it, 895,673 / 291,471 with Share and the link's dialogs; the encoder's chunk is 1,701 B raw / 908 B gzip, beside the fflate chunk Download already loads).
- **A `2.` link opens a base project with some files over it**, the encoding rocketh.dev's "Open in playground" buttons write: `#project=2.<base64url>`, where the JSON is `{"base": "bare", "files": {<path>: <text>}, "select": <path>}` (`base` and `select` optional; those three are the only keys a payload may hold), deflated with fflate at level 9, in base64url without padding, as `1.` is. Every object's keys are written in sorted order (JavaScript's default `sort()`, by UTF-16 code unit), so the same files always give the same link. Without `base`, the files go over the starting project (`startingProject()`); with `"base": "bare"`, over the bare base, `bareProject()` in `project/template.ts`: the starting project without its Counter sample (`contracts/Counter.sol` and `deploy/01_deploy_counter.ts`, `COUNTER_SAMPLE_PATHS`), so `rocketh/config.ts` and `rocketh/deploy.ts`, or the link's own. rocketh.dev's links all ask for bare, so an example opens as its own files and Deploy runs only its scripts. `bareProject()` throws when either Counter file is missing from the template, and a unit test calls it, so a template update that renames or removes one fails `pnpm verify` (and the release follower's pull request) instead of leaving `Counter` in every example; rocketh's `scripts/test-playground-examples.sh` keeps a copy of the list, so a change is made in both. The encoder, `encodeOverlay(files, select?, {base?: 'bare'})` in `project/overlay-link.ts`, writes `base` only when it is `'bare'` (a link without it is exactly the link written before `base` existed), throws on any other `base`, imports nothing but fflate, and refuses (throws) a link whose fragment would pass the 32 KB cap, so rocketh-website's site build fails on an example too big for a link. rocketh-website keeps a hand port of that encoder with JSDoc types (`web/open-in-playground/overlay-link.js`) and a copy of the decoder in its tests. Decoding (`decodeLink(value, {starting, bare})` in `project/share-link.ts`, which reads `1.` and `2.`, given both bases since which applies is known only once the payload is read) lays the files over the base, applies `1.`'s path rules to them (relative, no `..`, nothing under `deployments/`), and refuses a `select` that is not one of the resulting files, any key besides `base`, `files` and `select`, and a `base` other than `"bare"`; a `base` that is a string it does not know, or an unknown key, marks a link written for a newer playground (`NewerLinkError`), and a `base` of any other type a corrupted one. `files` may be empty, which opens the base as it is: the starting project, or for a bare link only `rocketh/config.ts` and `rocketh/deploy.ts` (Deploy then stops at the compile, since solc refuses a project with no Solidity source: "No input sources specified."). **The shared test vectors** are `test/lib/playground/overlay-link-vector.json` (no `base`) and `test/lib/playground/overlay-link-bare-vector.json` (the same files and `select`, `"base": "bare"`): each a fixed set of files, a `select`, and the exact `value` `encodeOverlay` must produce (`test/lib/playground/overlay-link.test.ts` checks both, and the e2e opens both). rocketh-website's encoder and test decoder are held to those same files, so a change to the encoding changes the vectors, here and there, together.
- **Opening a link runs nothing**, only Deploy does: its files go into the editor, the background compile hands the Solidity to solc as data, and no script runs. `project/open-link.ts` (a store, `test/lib/playground/share.test.ts`) decodes the fragment's `project` value once at start (a `2.` link over its base: the starting project, or for `"base": "bare"` the bare base, `createLinkOpener`'s `starting` and `bare`, which default to `startingProject()` and `bareProject()`), waits for the session to be `ready`, then calls `session.open(files, select)`, Reset's mechanism with the link's files in place of the starting project's, and the link's `select` selected (a `2.` link's; otherwise the first deploy script): a fresh chain at block 0, no records, the files saved over the reader's, so a link's contracts never meet another project's deployments. Over a project of the reader's own (saved files that are not the starting project, whatever base the link opens over) it asks first, offering Download, then Open or Cancel; Cancel keeps their files, chain and records and opens nothing. A first visit, or a project still the starting one, opens at once. A value that does not decode to project files (corrupted, cut short, an absolute path or one with `..`, a deployment record, or a `2.` link selecting a file it does not hold) is reported in the header and loads nothing. Once the link is opened, cancelled or found corrupted, the `project` key is removed from the URL (`kit/location.ts`, SvelteKit's `replaceState`; the other fragment keys are kept), so a reload shows the files as the reader left them rather than the link's. When the playground does not start, the key is kept, so a reload can still open it. So it is for a `2.` link refused only for a key or a `base` value this playground does not know: it was written for a newer playground, and the header says so and asks for a reload, which gets the newer build when a returning visitor's service worker first served a cached older one. Every other refusal removes the key.
- **The Contracts view** (`components/playground/Contracts.svelte`, loaded on demand) reads and calls the functions of each deployed contract. Its list is built from the records (`contracts/records.ts`: one entry per `deployments/playground/<Name>.json`, its address and ABI), so it follows a redeploy. Reads are `eth_call` on the node the session holds (`session.provider()`). A write is signed ON THE PAGE with a throwaway test key, through viem's local account over that node (`contracts/chain-calls.ts`: the page already holds the node, the keys are public, no user code runs on the page, and the EVM worker keeps exposing webevm's api unchanged), and only through `session.transact()`, which grants the chain while the session is `ready` (phase `sending` meanwhile), so a write never lands inside a run. The node mines each raw transaction at once (webevm's default `miningConfig: {type: 'auto'}`, the reason the runner passes rocketh `autoMine: false`), so the receipt is read straight after the send; a revert is caught by the gas estimate, decoded with the ABI, and nothing is sent. Who a write is sent from: the named accounts the last run resolved (`RunOutcome.namedAccounts`, reported by the runner, since the config is user code and the page never evaluates it), the deployer first; before any run, the test accounts labelled by index (`contracts/accounts.ts`).
- **The Transactions view** (`components/playground/Transactions.svelte`, loaded on demand) lists the in-tab chain's transactions, newest first, decoded with the records' ABIs (`transactions/decode.ts`): a deployment as "Deploy <name>" (found by the record's `transaction.hash`, or the receipt's `contractAddress`), a call as `<name>.<function>` with its named arguments, the events it emitted, a revert's reason, `from` labelled with the named account and `to` with the deployment's name; a transaction to an address no record holds is shown undecoded, with its selector. The list is a store (`transactions/transaction-list.ts`, one per session) that follows the session's `blockNumber`, which the session refreshes after it starts, after every run and after every write, the only ways a block is mined in the tab: no polling, and nothing read while a run sends. It reads 20 blocks below the head at first (a block holds one transaction under auto mining), then 20 more per "Show older", and catching up reads only the new blocks (more than a page of them starts it again from the head). It decodes with the records as they are now, again whenever they or the named accounts change: after a redeploy, an older transaction to the old address is undecoded unless some record still holds that address. A revert's reason is found by replaying the transaction at its block, so the node is created with webevm's `stateHistory` (`STATE_HISTORY_BLOCKS`, 256 blocks, persisted with the chain); older than that, the row says the reason is no longer available. Nothing in it writes to the chain.
- **Copied from jolly-roger**, each at the path it has there and saying so in its header, with the commit it was copied at. At commit a4082a13, unchanged below the header unless the header lists a change: the contracts page's `routes/contracts/components/FunctionInputs.svelte` and `routes/contracts/lib/input-errors.ts` (unchanged), and `ContractFunction.svelte` (the card, with its state moved to `contracts/function-call.ts` and the write half the playground's, as its header lists); the explorer's `routes/explorer/lib/services/blockScanner.ts`, `transactionDecoder.ts`, `transactionItem.ts` and `routes/explorer/lib/utils.ts` (unchanged: they take the chain and the contracts as parameters), with jolly-roger's `test/routes/explorer/decoding-display.test.ts`, `decoding-parameters.test.ts` and `test/routes/contracts/input-errors.test.ts`; and the ethereum UI, `core/ui/ethereum/` (`Address.svelte`, `AddressInput.svelte`, `TransactionHash.svelte`, `ImgBlockie.svelte` and their `address-input.ts`, `address-resolver.ts`, `ens.ts`), with what it imports: `core/capabilities/` (route, ENS and block explorer), `core/ens/types.ts` and `core/utils/ethereum/` (`blockExplorer.ts`, with its test, and `blockie.ts`). The playground provides no ENS and no block explorer, so `Address` and `TransactionHash` show the value with a copy button and no link. What differs in the playground (no wallet, the records as the contract list, the test keys, how the transactions are listed and labelled) lives in `contracts/` and `transactions/` here, not in edits to the copies. `contracts/` imports `src/routes/contracts/lib/utils.ts` from `$lib` on purpose: that is the copy's path in jolly-roger, and `src/routes/contracts/` and `src/routes/explorer/` have no `+page`, so they are no routes; keep it that way rather than moving the copies.
- **A hardhat-deploy v1 script is pointed to the migration guide.** When a run fails the way a v1 deploy script does, the session adds a line to the transcript after rocketh's own error, saying it looks like a v1 script and linking rocketh.dev's guide for v1 users, `https://rocketh.dev/hardhat-deploy/migration/` (`TranscriptLine.link`, which `Transcript.svelte` renders as a link opening in a new tab). `migration.ts` (plain `.ts`) recognises three shapes from the run's error as the runner reports it, a name and a message: the registry refusing an import of `hardhat`, `hardhat-deploy` (or a subpath of either, such as `hardhat/types` or `hardhat-deploy/types`) or `hardhat-deploy-ethers`, and a TypeError naming v1's `hre` API (`getNamedAccounts`, `getUnnamedAccounts`, `getChainId`, `deployments`), as `getNamedAccounts is not a function` or `hre.deployments.deploy is not a function`. A type-only import of `hardhat-deploy/types`, as v1's `DeployFunction` scripts have, is erased by the transpiler, so such a script fails on the second shape. The third is a script that fails before rocketh runs it, as a v1 `module.exports = async (hre) => {...}` script does: the runner's own error `<path> has no default export made with deployScript(...)` (`runner/run.ts`). A v2 script that forgot `deployScript(...)` gets that same error, so the session passes `looksLikeV1Script` the project files it ran, and the hint is added only when the script at that path is shaped like v1 (it names `hre`, `HardhatRuntimeEnvironment`, `getNamedAccounts`, `getUnnamedAccounts`, `getChainId` or `deployments`); otherwise the error stands alone. Any other error gets no such line. `test/lib/playground/v1-script.test.ts` runs each shape, and ordinary errors, through the real pipeline. The header also has a "Migrating from hardhat-deploy v1?" link to the same guide, always shown.
- **User code runs only in the runner.** It resolves imports through `runner/registry.ts`: relative paths to project files, the packages in `runner/bare-modules.ts` (each a lazy chunk, loaded before a run that imports it), and nothing else, with an error naming the import and the list.
- **The config is the reader's**, with the accounts replaced by the throwaway keys in `runner/test-keys.ts`, the in-tab chain declared and the environment named `playground` (`runner/compose-config.ts`).
- **rocketh's transcript** needs a `named-logs` factory installed before any rocketh module is evaluated: `runner/log-hook.ts`, the runner's first import.
- **Bundle budgets.** `pnpm verify` runs `scripts/bundle-budgets.mjs` (`pnpm web:budgets`) after `web:build`, since the unit tests run before there is a build, and it fails when a bundle has grown past its budget, naming the bundle, its size and its budget. It measures, raw and gzip (level 9), the files in `.svelte-kit/output/client`: the first load (the static import closure, JS and CSS, of SvelteKit's entries, the root layout's node and the root page's node, from the client manifest `.vite/manifest.json`); each part loaded on demand (every `dynamicImports` target the first load reaches, SvelteKit's own nodes aside, as its closure minus the first load: the Contracts view, the Transactions view, Download's zip and Share's encoder); each of the four workers of `workers.ts` (a worker is its own build with no manifest, so its entry is found by name and its closure read from the emitted files' relative imports); each package of `runner/bare-modules.ts` the runner loads lazily (its chunk's closure minus the runner's); the TypeScript worker's declarations asset; and the shipped soljson. Each budget is the size measured when the check landed, written in the script with the date, plus 10%. Raising one is a reviewed edit of its line: `node scripts/bundle-budgets.mjs --measure` (from `web/`, after a build) prints every entry as measured now. A new on-demand part, worker or runner package with no budget fails the check, as does a budget whose bundle is gone; `test/bundle-budgets.test.ts` checks the measuring on a small build and that the budgets name every worker and runner package. Measured on 2026-11-20: first load 895,667 B raw / 291,466 B gzip; Contracts 344,034 / 103,325 and Transactions 332,926 / 101,345 on demand; the TypeScript worker 3,484,391 / 968,786, the EVM worker 479,564 / 140,703, the runner 10,943 / 4,634, the compiler worker 3,443 / 1,576; the declarations 11,906,743 / 1,169,639 (14,658,446 / 1,408,184 since 2026-11-21, with `@rocketh/router`, whose types import solidity-proxy's artifact index and with it every artifact's literal type; the runner's `@rocketh/router` chunk is 454,246 / 133,056, loaded only by a run that imports it); soljson 9,169,169 / 6,520,140.
- **The starting project** is `web/project-template/`, the published hardhat-deploy template, unedited (`project/template.ts`, refreshed by `scripts/update-project-template.mjs`). **The compiler** is the soljson pinned in `web/solc.json`, copied into `static/solc/` by `scripts/soljson.mjs`.
- **Following rocketh releases.** `.github/workflows/follow-rocketh-releases.yml` runs daily and by hand (`workflow_dispatch`). `scripts/follow-releases.mjs` (plain node, `test/follow-releases.test.ts` with the registry stubbed) asks npm for the `latest` dist-tag of `rocketh`, every `@rocketh/*` package `web/package.json` pins (each must be pinned exactly) and `hardhat-deploy` (the starting project's release, in `project-template.json`); `webevm` and `viem` are not followed. A version with a prerelease identifier (`-beta.0`) is never taken, nor one at or below the pin. A newer rocketh package is pinned exactly in `package.json`; a newer hardhat-deploy refreshes the starting project with `scripts/update-project-template.mjs <version>` (the declarations are rebuilt by every build). The bump branch's name follows from the versions (`follow-releases/rocketh-core-0.26.2-rocketh-0.26.5`, a hash of them when that would pass 200 characters), and when `origin` already has it the run stops there, so a pull request is opened once per set of versions. Otherwise the workflow updates `pnpm-lock.yaml` (`pnpm install --lockfile-only`), runs `pnpm verify` and `pnpm test:export` on the change, and only when both pass opens a pull request against the branch the run started from, saying in its body when the refreshed template's solc differs from `solc.json`. A maintainer reviews and merges it; nothing merges itself. It uses no personal token and no secret, only the run's `GITHUB_TOKEN`, with per-job permissions: the job that bumps and tests reads only and hands the tested change to the next as a patch, and only the job that pushes the branch and opens the pull request can write. Opening it needs the repository setting "Allow GitHub Actions to create and approve pull requests" (Settings, Actions, General, Workflow permissions). A pull request opened with `GITHUB_TOKEN` starts no other workflow, which is why the tests run inside this one.

Design: `work/specs/tasked/rocketh-playground.md` (remaining work in `work/tasks/`), and the runner spike, `docs/spikes/runner/` on branch `spike/runner`.
