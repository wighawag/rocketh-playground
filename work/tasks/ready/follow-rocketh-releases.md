## What to build

The spec's decision "Following rocketh releases": a scheduled GitHub workflow in this repository checks npm for new versions of the rocketh packages `web/package.json` pins and of `hardhat-deploy` (the starting project's version, recorded in `web/project-template.json`), bumps them, refreshes the starting project with `web/scripts/update-project-template.mjs <new hardhat-deploy version>` (the TypeScript declarations are regenerated by every build), runs `pnpm verify` and the export test (`pnpm test:export`), and opens a pull request a human merges. Auto-merge is out until the gate has proved itself.

**No personal token (maintainer decision, 2026-11-20).** The workflow uses only the `GITHUB_TOKEN` GitHub gives every run: reading npm needs no token, and the pull request is opened with `GITHUB_TOKEN` once the maintainer turns on the repository setting "Allow GitHub Actions to create and approve pull requests" (Settings, Actions, General, Workflow permissions). Nothing in the repository holds or names a personal token or a secret. Permissions are granted per job, the least that work: the job that checks and tests reads only (`contents: read`); only the job that pushes the bump branch and opens the pull request gets `contents: write` and `pull-requests: write`. A pull request opened with `GITHUB_TOKEN` triggers no other workflow, which is why the tests run inside this workflow before it opens one. It runs on a schedule (daily) and on `workflow_dispatch`, and does nothing when an open pull request from it already exists for the same versions.

**What is built and tested here, and what the maintainer does.** The deciding logic is a plain node script (for example `web/scripts/follow-releases.mjs`): given `web/package.json`, `web/project-template.json` and the npm registry's answers, it says which packages have a newer published version and applies the bump to the files; it is tested in node with the registry stubbed (nothing new, one rocketh package newer, hardhat-deploy newer). The workflow file (`.github/workflows/follow-rocketh-releases.yml`, in the style of `.github/workflows/pages.yml`: actions pinned by SHA, per-job permissions) calls that script, then the template refresh, the tests and the pull request. The maintainer merges the workflow (every CI workflow is theirs to approve), turns the setting on, and runs it by hand once; the build cannot run it on GitHub.

## Acceptance criteria

- [ ] The bump script, tested in node with npm stubbed: nothing newer changes nothing; a newer rocketh package is pinned exactly in `web/package.json`; a newer `hardhat-deploy` updates `web/project-template.json` through `update-project-template.mjs`; a version npm marks as a prerelease is not taken.
- [ ] The workflow uses only `GITHUB_TOKEN`, with per-job permissions as above, actions pinned by SHA, a daily schedule and `workflow_dispatch`, and it opens no pull request when nothing is newer or one for the same versions is already open.
- [ ] `web/src/lib/playground/README.md` (or the repository README) says how releases are followed and names the repository setting the workflow needs.
- [ ] After merge (the maintainer, not the build): run by hand on a branch with an outdated pin, it opens a pull request bumping it, with the tests and the export test green.
